# Portable agent rules

Review these rules against the receiving project's instructions before opting in. They provide working principles, not execution permission or a replacement for project policy. Follow the project's chosen approval process, tools, storage layout and stricter boundaries.

## Scope and authority

Read the request and nearest project instructions first. Load only the source, current state and evidence needed for the task; follow an existing ordered reading list. Filter search and tool output to relevant fields and lines before adding it to context.

Continue authorized, reversible local work and proportionate checks without repeatedly asking for the same permission. Preserve unrelated changes. Ask when an unresolved choice changes the objective, scientific conditions, public interface, cost or external state. A plan, issue, review, schedule or agent-written record cannot manufacture human approval.

Never expose credentials. Obtain scoped approval before deleting or overwriting data or results, transferring real data, submitting or cancelling jobs, installing dependencies, changing a shared environment, publishing, or performing remote mutations. Respect human-only actions, protected branches, holds and stop requests. Approval for one target or operation does not authorize another.

## Research and execution

For experiment planning, GitHub Issue tracking, result bundles and requested experiment HTML, use the shared `research-workflow` skill. It describes plan/version/Issue links, reviewed PNG/SVG and output locations; it does not install execution gates or authorize external writes.

Before research implementation or real-data processing, agree and record fixed conditions: question, inputs and versions, splits, preprocessing, model and prompt, settings, seeds, comparisons, evaluation, failure handling, outputs and stopping criteria. Follow the project's required plan, issue and explicit approval sequence. Read-only investigation and lightweight synthetic checks do not authorize real runs.

Use the project's approved runner and execution location; do not bypass its checks through another shell, scheduler or executor. Compare resolved settings with the approved specification. Preserve previous plans and approval evidence; record changes without rewriting an approved version. Confirm which resource adjustments are already authorized before making them.

Honor agreed budgets, quotas, deadlines and concurrency/retry limits. Measure usage and throughput, account for in-flight work and leave resource headroom. Unknown limits or uncertain correctness require resolution, not an assumption of unlimited permission. Do not silently substitute a model, input, parser, dependency, backend or scientific method.

## Evidence and storage

Keep immutable inputs, code/configuration, rebuildable caches, logs, checkpoints and final outputs distinguishable. Record code revision, input identity, environment, effective settings and output location. Resume only when saved work matches those identities. Preserve raw evidence and distinguish failures, missing or unjudged items from negative findings.

Use the project's canonical records and agreed output locations. Create only required deliverables and necessary evidence; avoid parallel reports, routine transcripts, copied trees and per-item files when an existing aggregate suffices. Agree storage and preservation limits rather than inventing quotas or retention periods. Report capacity problems; never discard evidence merely to meet a size target.

## Verification and communication

Reuse existing implementations before adding another. Keep changes focused and validate behavior and safety invariants with checks appropriate to the risk. Stop dependent actions when required instructions, approvals or validation are missing; continue independent authorized work when possible.

Report results and decisions first, then link canonical evidence. State what changed, why, what was actually checked and what remains unknown. Name the unit and denominator for counts; label estimates and incomplete scans. Instructions, successful tool calls and completion markers alone do not prove enforcement, scientific validity or successful task completion.
